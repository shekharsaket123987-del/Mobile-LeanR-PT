# Audit Section 10: Admin Leave Requests — Screen-Level Parity

Scope: Admin "Leave Requests" screen only. Web: `src/app/admin/leave-requests/page.tsx` + `src/components/admin/LeaveRequestsClient.tsx` + `src/lib/actions/admin-leave.actions.ts` (LeanR-PT-main). Mobile: `src/app/(admin)/leave.tsx` + `src/lib/data/admin-leave.ts` (leanr-mobile-app). Cross-reference: `mobile-app-reference/audit/05-admin-coach-crossdeps-navigation.md` §A7 already confirmed the underlying `resolveLeaveRequest()` cascade-triggering mechanics (approve→cascade, reject→no cascade) as WORKING CORRECTLY at the data layer — this pass covers the screen itself, which that pass did not.

## Findings

**LVE-001 — List scope and fields.** Web (`admin-leave.actions.ts:26-43`) lists PENDING requests only (no archive/filter view) with `coachName`, `startsOn`/`endsOn`, `leaveType`, partial start/end time, `reason`, `submittedAt`. Mobile `getPendingLeaveRequests()` (`admin-leave.ts:31-56`) queries `coach_leave` with `.eq('status', 'pending')` and returns the identical field set (plus `coachId`, needed for the review-clients link — see LVE-004). **WORKING CORRECTLY.**

**LVE-002 — Date formatting and long-leave badge.** Web (`LeaveRequestsClient.tsx:124-132`) formats dates via `formatDate()` and shows a `{days}+ days` badge on the card itself when `leaveType==='full_day'` and duration ≥ `LONG_LEAVE_THRESHOLD_DAYS` (14). Mobile `leave.tsx` (`:36-38, 58, 108-111`) defines the identical threshold/duration helper and `formatDate()`, and both are wired into the card render (date range formatted, badge appended to the coach-name line as `· {n}+ days`). **WORKING CORRECTLY** (verified in current file state — both helpers are live, not dead code).

**LVE-003 — Submitted timestamp.** Web shows "Submitted {formatDate(submittedAt)}" per card (`LeaveRequestsClient.tsx:145`). Mobile shows the equivalent `Submitted {formatDate(request.created_at)}` (`leave.tsx:117`, `styles.submitted`). **WORKING CORRECTLY.**

**LVE-004 — Approval outcome summary.** Web shows an inline success `Card` after approval (`LeaveRequestsClient.tsx:56-109`) listing auto-assigned client→shadow-coach pairs (with each shadow coach's covered date range), unassigned/needs-manual clients (with their specific uncovered dates) plus a "Review clients" link to `/admin/coaches/{coachId}`, a "no clients affected" fallback message, and the long-leave nudge repeated in the result panel. Mobile (`leave.tsx:60-104`) builds the equivalent content as a native `Alert.alert` (auto-assigned list, needs-manual list, no-clients-affected fallback, long-leave nudge text) with a "Review clients" action button that navigates to `/coaches/[id]` with `request.coachId` when there are unassigned clients — a reasonable native-idiomatic adaptation of web's inline card (per-platform presentation, same information and same action), acceptable under this task's UI/UX-parity rules (functional parity required, not pixel-identical layout). **WORKING CORRECTLY, adapted presentation.**

**LVE-005 — Missing data richness in the outcome payload (gap, not fixed here).** Web's `LeaveResolutionSummary` (`availability.service.ts`, referenced via `LeaveResolutionSummary` import in `LeaveRequestsClient.tsx:12`) carries, per auto-assigned client, the shadow coach's own covered date range (`sc.startsOn`/`sc.endsOn`), and per needs-manual client, the specific `uncoveredDates` list. Mobile's `LeaveCascadeOutcome` type (`admin-shadow.ts:488-491`) only carries `{clientName, shadowCoachName}` for auto-assigned and `{clientName}` for needs-manual — no per-assignment date ranges, no uncovered-dates list. `leave.tsx`'s Alert therefore cannot show these (there's no data to show). **Status: IMPLEMENTED BUT DIFFERENT FROM INTENDED WORKFLOW (narrower data, not narrower functionality)** — admin still sees who's covered and who needs manual attention, just not the exact date sub-ranges inline.
  - **Not fixed in this pass**: `admin-shadow.ts` (owner of `LeaveCascadeOutcome` and `runLeaveApprovalCascade`) is out of this task's scope — it's the Shadow Coverage module's file, edited under a separate task in this same sweep. Enriching the outcome shape to carry dates requires coordinated changes there. **Requires follow-up**: extend `LeaveCascadeOutcome` with per-assignment `startsOn`/`endsOn` and per-needs-manual `uncoveredDates: string[]`, threaded through from `runLeaveApprovalCascade`'s existing internal computation (it already tracks per-occurrence coverage to build the current summary — the raw dates are almost certainly already in scope inside that function, just not surfaced on the return type).

**LVE-006 — Reject path.** Web: reject just calls the action, no confirmation modal, updates the list via `router.refresh()`. Mobile: reject calls `resolveLeaveRequest(id, 'rejected')` directly (`leave.tsx:60-64`), no confirmation modal, reloads via `onResolved()`. **WORKING CORRECTLY** (matches web's lack of a confirmation step — the task's own PRD comment at `admin-leave.ts:10` confirms this is intentional: "Rejecting a leave never cascades, per the PRD").

## Requires product/schema decision

None — LVE-005 is a code-only enhancement (no schema change), just cross-file (belongs with the Shadow Coverage task's ownership of `admin-shadow.ts`), tracked as a follow-up rather than implemented in this pass to avoid concurrent-edit conflicts with that task.
